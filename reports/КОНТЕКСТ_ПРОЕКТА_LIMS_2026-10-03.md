## 2. Бизнес-цель системы

Система не является заменой Damumed, 1С или ЛИС анализаторов.

Ее задача — показать руководителю лаборатории доказуемую операционную картину:

```text
Damumed journals      → зарегистрированные/выполненные услуги, TAT, подразделения
Analyzer event logs   → фактические датированные события приборов
1С read-only snapshot → бухгалтерские остатки, склады, серии, номенклатура
```

Из этих контуров строятся:

- операционные KPI;
- TAT по услугам;
- покрытие источников;
- только доказуемая сверка `штрих-код / направление / дата`;
- расчетный расход реагентов по нормам;
- прогноз покрытия подтвержденных упаковок 1С;
- evidence-first ответы помощника директора.

### 2.1. Что система не должна делать

- не ставить диагнозы;
- не делать клинических рекомендаций;
- не объявлять сотрудника виновным;
- не считать отсутствие лога доказательством нецелевого запуска;
- не считать `errors.xml` датированным фактом выполнения;
- не придумывать фактическое списание 1С;
- не связывать пациента с конкретной партией 1С без первичного источника;
- не создавать обязательные закупки или заказы на основании расчетной модели;
- не выдавать suggested mapping за подтвержденную упаковочную связь.

## 3. Основные правила доказательности

### 3.1. Отсутствие источника не равно расхождению

Если за дату есть лог анализатора, но нет датированного журнала Damumed, статус:

```text
NO_COMPARABLE_EVIDENCE
```

означает:

> Сверка ожидает второй источник. Данные не пригодны для сравнения, но это не «расхождение», не «потеря» и не «левый анализ».

Для текущей больницы это штатная ситуация, потому что:

- логи анализаторов поступают автоматически;
- Damumed пока не интегрирован по API;
- журналы Damumed загружаются вручную, обычно в конце месяца;
- новые события анализаторов могут появиться раньше, чем соответствующий месяц окажется в загруженном журнале.

### 3.2. Точная связь источников

Положительное доказательство связи:

```text
barcode анализатора
      =
номер направления Damumed
      +
та же календарная дата
```

Если анализатор передает `ServiceMo.Code`, `ServiceID` или `OrderResearchID`, это усиливает связь услуги.

Если направление содержит несколько услуг, а анализатор не передал ID/код услуги, нельзя честно приписывать прогон одной конкретной услуге. Исключение — направление с единственной услугой; оно помечается как referral-derived candidate, а не как прямой analyzer service ID.

### 3.3. 1С не является пациентским контуром

Верная модель:

```text
услуга Damumed
  → расчетный расход по норме
  → подтвержденная упаковочная связь
  → агрегированный остаток 1С
```

Неверная модель:

```text
пациент → проба → конкретная партия 1С
```

Последняя цепочка не доказуема текущими источниками и не должна имитироваться.

### 3.4. Suggested mapping

`SUGGESTED` mapping:

- виден пользователю;
- может показать расчетный расход Damumed;
- не участвует в арифметике покрытия;
- не дает дни покрытия;
- не превращается в `CONFIRMED` без подтвержденной емкости упаковки именно у номенклатуры 1С.

## 4. Контуры данных и фактические источники

## 4.1. Damumed

### Назначение

Damumed — источник операционных данных:

- услуги;
- номера направлений;
- статус;
- даты получения и выполнения;
- подразделения;
- материал;
- TAT;
- стоимость услуги;
- исполнитель;
- журнал выполненных исследований;
- журнал регистрации направлений.

### Текущая загрузка

API-интеграции Damumed пока нет.

Текущий режим:

```text
manual monthly upload
```

То есть журнал загружается человеком, обычно после завершения периода.

### Форматы

Поддерживаются:

- CSV Windows-1251, `;`-разделитель;
- XLS;
- XLSX.

Для CSV журналов реализовано позиционное соответствие колонок:

```text
Журнал направлений:
  referral_number, patient_iin, patient_name, department,
  service, material, status, received_at, completed_at

Журнал выполненных исследований:
  referral_status, patient_iin, patient_name, sample_collected_at,
  department, service, referral_number, completed_at,
  result_text, performer, funding_source, price, quantity, total
```

### Персональные данные

Raw Damumed файлы и raw/normalized cells могут содержать:

- ИИН;
- ФИО;
- дату рождения;
- диагноз;
- историю болезни;
- номер направления;
- текст результата;
- сведения о сотруднике.

Эти данные не должны уходить в Director Assistant или 1С snapshot.

## 4.3. `errors.xml`

`errors.xml` — это не append-only журнал.

Он является текущим контекстным снимком:

- может содержать результат;
- может содержать Device/SystemName;
- не хранит надежное время фактического прогона для каждой пробы.

Поэтому:

```text
errors.xml ≠ датированный analyzer event
```

Новая загрузка `errors.xml` заменяет предыдущую DB запись этого analyzer, чтобы snapshot не накапливался как история.

## 4.4. 1С read-only mart

### Цель

В backend не загружается `.dt` и не дается прямой доступ к raw 1С базе.

Цепочка:

```text
1С isolated mart lims_ro
  → onec-readonly-snapshot.json
  → POST /api/onec/snapshots/read-only
  → onec_readonly_snapshots
  → stock coverage API
```

### Экспортируемые сущности

- номенклатура;
- складские остатки;
- склады;
- серии;
- срок годности;
- стоимость;
- контрагенты;
- source checksum;
- период и дата актуальности.

### Намеренно пустые сущности

Текущий exporter отдает:

```json
"receipts": [],
"writeOffs": []
```

Причина: направление движения и бухгалтерская семантика еще не подтверждены бухгалтером/первичным источником.

Следствие:

- нельзя показывать реальные приходы 1С;
- нельзя показывать реальные списания 1С;
- нельзя сравнивать расчетный расход с подтвержденным списанием;
- можно показывать остатки и расчетное покрытие.

### Критичная audit-граница

В доступных репозиториях отсутствует versioned DDL для `lims_ro.*`.

Поэтому пока не доказано:

- какие raw 1С таблицы участвуют в views;
- нет ли patient-linked join;
- как фильтруются deleted/inactive records;
- является ли stock snapshot точкой во времени;
- какая warehouse policy применяется;
- какие остатки доступны лаборатории.

Правильная формулировка:

> JSON snapshot задуман как sanitized read-only export. Отсутствие ПДн в raw 1С базе пока не доказано без DDL и проверки views.

## 6. Операционные периоды Damumed

### Прежняя проблема

UI показывал:

```text
День
Неделя
Месяц
```

без фактических границ. Поэтому число недели могло быть больше числа месяца и выглядело ошибкой.

### Причина

Периоды строятся не от даты браузера, а от максимальной business date последнего нормализованного журнала Damumed:

```text
completed_at
  → received_at
  → referral/registration date
```

Неделя может захватывать конец предыдущего месяца.

### Исправление

Fast KPI API теперь возвращает:

```json
{
  "period": "week",
  "referenceDate": "...",
  "periodFrom": "...",
  "periodTo": "...",
  "periodLabel": "..."
}
```

Текущий production smoke-test:

| Срез | Реальный диапазон | Услуг | Результатов |
|---|---:|---:|---:|
| День | 03.09.2026 | 2 354 | 1 894 |
| Неделя | 31.08.2026 — 03.09.2026 | 9 489 | 8 449 |
| Месяц | 01.09.2026 — 03.09.2026 | 6 931 | 6 007 |

Следовательно:

```text
Неделя > месяц
```

в этом срезе корректно, потому что неделя включает 31 августа, а месячный срез начинается 1 сентября.

## 7. Сверка источников и задержка ручных журналов

## 7.1. Исправленная модель

Новые analyzer events не становятся `DISCREPANCY`, если для их даты нет Damumed completed journal.

Они остаются:

```text
NO_COMPARABLE_EVIDENCE
```

UI показывает:

```text
Ожидает журнал Damumed
```

а не:

```text
Нет журнала / критическая ошибка / расхождение
```

## 7.2. Поздняя месячная загрузка

Ранее event listener пересчитывал только:

```text
today - 29 days ... today
```

Это неверно для поздно загруженного исторического месяца.

Исправлено:

```text
successful Damumed normalization
  → DamumedReportNormalizedEvent
  → min(completed_at) ... max(completed_at) именно этого upload
  → reconciliation rebuild по фактическим датам файла
```

Теперь:

- CSV публикует event;
- XLS/XLSX normalizer также публикует event;
- только `COMPLETED_LAB_STUDIES_JOURNAL` запускает reconciliation rebuild;
- referral registration journal остается операционным источником, но не становится ложным coverage source.

## 7.3. Пересекающиеся monthly uploads

Ранее разные запросы reconciliation использовали разные правила:

- coverage — только latest upload;
- referral/service query — все normalized uploads.

Это могло:

- удваивать service counts;
- подтверждать referral из старого файла;
- одновременно показывать «нет coverage».

Исправлено правило:

```text
для каждой completed date выбрать один latest successfully normalized upload
```

Это применяется к:

- coverage;
- service stats;
- referral keys;
- referral service candidates;
- period index.

## 8. Director Assistant

## 8.1. Назначение

Помощник директора отвечает только по агрегированному evidence packet:

- операции Damumed;
- устойчивый TAT;
- coverage sources;
- 1С snapshot metadata;
- число confirmed/suggested mappings.

Не передаются:

- ФИО;
- ИИН;
- номер направления;
- raw barcode;
- raw result;
- полный 1С snapshot;
- содержимое Damumed строк.

## 8.2. История чата

Ранее история хранилась только в browser `localStorage`.

Теперь:

```text
director_assistant_messages
```

в PostgreSQL, отдельно по `user_login`.

API:

```text
POST   /api/director-assistant/ask
GET    /api/director-assistant/history?limit=...
DELETE /api/director-assistant/history
```

Frontend показывает полноценный чат:

- пользовательские сообщения;
- сообщения помощника;
- typing state;
- server-side history;
- кнопка очистки;
- evidence cards;
- диапазон источников;
- TAT mini-bars;
- mapping summary.

## 8.3. Защита вопроса

До отправки в provider блокируются:

- 12-значный ИИН;
- маркеры пациента;
- ФИО;
- история болезни;
- номер направления;
- barcode/штрих-код.

Это provider-neutral политика: смена Azure/OpenAI-compatible provider не меняет бизнес-границу.

## 8.4. Исправление старого AI-ответа

Старый ответ смешивал:

```text
операционный месяц = 6 931
полная старая registration summary = 61 137
```

и упоминал десятки тысяч `NO_COMPARABLE_EVIDENCE` как зону внимания.

Это было вводящим в заблуждение.

Новая логика:

- period reconciliation строится вокруг фактических source dates;
- при `WAITING_FOR_MONTHLY_DAMUMED_JOURNAL` assistant не цитирует `noComparableEvidence`, `analyzerEvents`, `reconciled=0` как проблему;
- вместо этого говорит, что сверка ожидает ручную загрузку журнала;
- assistant не сравнивает полную historical summary с выбранным операционным периодом.

## 8.5. TAT

Правило для Assistant:

- только сервисы с минимум 10 наблюдениями;
- median + p90 + count;
- не использовать термин «максимальный TAT»;
- не делать вывод по единичной записи;
- при outlier-sensitive series показывать ограничение.

Production test assistant:

- корректно определил `WAITING_FOR_MONTHLY_DAMUMED_JOURNAL`;
- не назвал новые analyzer events расхождениями;
- показал услуги TAT с выборкой 12–29 наблюдений;
- history test entries были очищены после smoke-test.

```text
      день
        analyzer
          raw files
```

Отдельно отображаются:

- `Applogs` — датированные events;
- `errors.xml` — contextual XML snapshot;
- Damumed period внутри файла;
- event period analyzer file;
- status parse/normalization.

Coverage table теперь явно объясняет:

> Damumed загружается вручную в конце месяца. Новые analyzer logs до загрузки второго источника ожидают сверку и не являются расхождением.

## 9.4. Network/UX resilience

Добавлено:

- request timeout:
  - обычный API: 45 секунд;
  - FormData upload: 5 минут;
  - Director Assistant: 90 секунд;
- понятная timeout ошибка вместо бесконечного loader;
- очистка QueryClient при logout/session change;
- очистка локального reagent state при отсутствии token;
- Reports refresh обновляет и Damumed uploads, и analyzer log uploads.

## 9.5. Язык аналитики логов

Термины изменены:

| Было | Стало |
|---|---|
| Несанкционированный | Сигнал для сверки |
| Несанкционированное потребление | Расчетное потребление по сигналам логов |
| Расхождение | Кандидат/сигнал для сверки |
| Потеря реагентов | Расчет по нормам, не подтвержденный write-off |

Это важно: лог без journal coverage не должен обвинять сотрудника или создавать финансовый вывод.

## 17. Заключение

Система перешла из состояния «интерфейс поверх разрозненных источников» в состояние evidence-first operational platform:

- есть production deployment;
- есть автоматический hospital log ingestion;
- есть корректная граница no-comparable evidence;
- есть manual monthly Damumed model;
- есть read-only 1С snapshot model;
- есть server-side AI history;
- есть явные period boundaries;
- есть UI, который меньше имитирует факты.

Однако финальная надежность зависит не от еще одного красивого экрана, а от трех внешних подтверждений:

```text
1. фактический DriversManager → analyzer identity mapping;
2. DDL/grants sanitised 1С mart;
3. регулярное доказуемое покрытие Damumed + analyzer dates.
```

До этого система должна честно говорить:

> «Источник ожидается», «расчетная модель», «требует проверки», а не «доказано нарушение».
